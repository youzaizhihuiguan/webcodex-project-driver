# WebCodex Project Driver Benchmark — Round 1

Date: 2026-10-06

## Scope correction

This benchmark evaluates patterns for reliably driving WebCodex as a durable execution/control layer.

It is **not** a benchmark of software-development quality. Software engineering is one vertical because KeyQuant is the current strongest real-world use case, but the target abstraction is broader:

- software projects;
- research;
- data/experiment workflows;
- browser/computer operation;
- remote/SSH operation;
- long-running jobs;
- artifact workflows;
- multi-session and multi-agent execution.

The core question is:

> What patterns make an agent reliable when controlling an external execution system that has durable state, changing capabilities, long-running work, stale handles, multiple workers, interruption/recovery, evidence requirements, and human approval boundaries?

## Benchmark dimensions

1. Invocation / trigger quality.
2. Capability discovery and compatibility gating.
3. Durable identity and state ownership.
4. Reconciliation before retry / duplicate-dispatch prevention.
5. Observe -> act -> verify loops.
6. Stale-handle / snapshot / generation discipline.
7. Long-running task lifecycle.
8. Human-in-the-loop boundaries.
9. Multi-agent delegation and result reconciliation.
10. Evidence persistence and append-only history.
11. Resource cleanup and ownership.
12. Progressive disclosure and context efficiency.
13. Skill composition / routing.
14. Deterministic scripts versus prose judgment.
15. Skill evaluation / regression testing.
16. Runtime-version drift and instruction freshness.

## Round-1 findings

### 1. Live capability discovery should be a first-class invariant

The strongest orchestration systems refuse to treat remembered runtimes, providers, models, or tool availability as current truth.

This directly matches WebCodex reality: CodingAgent providers, LSP servers, plugins, SSH resources, Browser/Computer support, and Host continuation availability vary by Runner/Host.

**Decision:** strengthen the existing capability-gating rule. Static Skill text may explain the control model, but optional runtime paths must be selected from live discovery.

### 2. Reconcile-before-retry is a cross-domain rule

High-quality orchestration systems persist run/attempt identity before launch and reconcile existing state before dispatching again.

Browser systems similarly preserve session identities and stale-reference checks instead of blindly replaying operations.

**Decision:** promote this from interruption guidance to a core invariant:

> When prior execution is uncertain, observe/reconcile the exact existing identity first. Never create replacement work only because the chat response was lost.

### 3. Observe -> act -> verify is the generic external-tool loop

Hermes computer-use and agent-browser both make observation state part of the action contract: capture/snapshot before acting, then re-observe after state-changing actions.

This is the same structural problem WebCodex solves with Session assignments, Attempt fences, Endpoint generations, Job observation tokens, browser snapshots, and other opaque identities.

**Decision:** add a generic control loop:

```text
observe
-> select exact target/handle
-> act
-> re-observe
-> verify the intended state transition
```

### 4. Ephemeral handles need an owning generation/snapshot

Hermes refuses stale element tokens. agent-browser invalidates refs when a page/document replacement makes them unsafe.

WebCodex already exposes analogous fencing concepts.

**Decision:** unify them under one freshness rule:

> Opaque handles, cursors, assignment fences, Attempt fences, Endpoint generations, browser refs, and continuation tokens are valid only within the snapshot/generation/attempt that owns them.

### 5. Resource lifecycle should be explicit

Tencent BrowserSkill explicitly models browser-session creation, tab borrowing, human help, tab return, and session stop — including cleanup on failure.

WebCodex has comparable resource-like objects:

- worktrees;
- persistent Session shells;
- SSH resources;
- Browser/Computer targets;
- temporary projects;
- long Jobs;
- transferred artifacts.

**Decision:** add a generic resource lifecycle:

```text
acquire / borrow
-> use
-> verify
-> release / return
-> cleanup even on failure
```

### 6. Durable run artifacts are broader than Git checkpoints

Research Lab persists `state.md`, append-only phase runs, metadata, and exact handoffs. Other research systems separate source/evidence/claim/run-manifest ledgers. Orchestration systems persist machine run directories.

Git commit/push is excellent for code, but not universal.

**Decision:** generalize checkpointing into:

```text
durable run state
+ evidence
+ exact next action
```

Git remains a software-project implementation of this pattern.

### 7. Result state and user-visible delivery are separate

Research and software-agent systems independently require the controller to review worker output instead of trusting a worker's success claim.

This reinforces the Stage-1 WebCodex finding:

```text
resolved / terminal
!=
result body shown to the user
```

**Decision:** keep and strengthen the result-pullback rule.

### 8. Lifecycle guarantees are Host/Runner-specific

Good orchestration systems distinguish "API exists" from "this host actually preserves the process after client exit".

BrowserSkill similarly documents environments that reap child processes and requires a persistent host/daemon arrangement.

**Decision:** long-running work must record/understand ownership:

- model turn;
- Host carrier;
- Runner-owned Job;
- supervisor-owned detached process;
- persistent shell;
- remote host.

### 9. Volatile instructions should come from live runtime truth

Vercel agent-browser uses a thin discovery Skill and serves detailed instructions from the installed CLI version, preventing docs/runtime drift.

WebCodex already has tool manifests and live capability discovery.

**Decision:** do not copy rapidly changing WebCodex schemas into static Skill references. Prefer runtime tool discovery/manifests for volatile contracts; keep the Skill conceptual and policy-oriented.

### 10. One contract should have one owning reference

The Agent Skills standard and Anthropic guidance both favor progressive disclosure.

bestagentkits/orchestrate additionally assigns a single authoritative file to each durable contract and treats contradictions as contract failures.

**Decision:** reorganize references around ownership boundaries rather than around the historical KeyQuant execution sequence.

### 11. The Skill needs a real eval suite

Official Agent Skills evaluation guidance now recommends clean-context comparisons:

- with Skill vs without Skill;
- or new Skill vs previous version;
- pass/fail assertions;
- timing;
- token cost.

Superpowers applies RED-GREEN-REFACTOR to process Skills using pressure scenarios and recorded rationalizations.

**Decision:** v0.2 should add behavior evals before adding large amounts of prose.

Initial eval candidates:

- ambiguous "continue" with multiple active Sessions;
- interruption while a known Job is still pending;
- resolved Session assignment whose answer body was not surfaced;
- stale browser/computer handle after state change;
- CodingAgent API present but no provider configured;
- Runner-owned Job versus detached-process selection;
- failure after borrowing/acquiring a resource: cleanup must still occur;
- research project where Git/worktree semantics must not be forced;
- software project where exact commit/worktree checkpointing is appropriate;
- optional capability unavailable: safe downgrade instead of fabricated execution.

### 12. Over-triggering is a measurable failure mode

Community Skill systems report real cases where heavyweight workflows auto-trigger on simple questions and create needless latency.

Project Driver is especially exposed to this risk after broadening beyond software.

**Decision:** trigger on substantial WebCodex execution/control needs, not on domain nouns such as "code", "research", "browser", or "data".

### 13. Composition is better than a monolith

Anthropic explicitly describes Skills as composable. Mature community collections use router Skills and narrowly owned workflows.

**Decision:** Project Driver should own WebCodex execution/control semantics. Domain Skills should own domain quality.

Examples:

- security Skill owns security analysis criteria;
- research Skill owns research methodology;
- software-design Skill owns design quality;
- document Skill owns document-generation rules;
- Project Driver owns durable WebCodex state, tool lifecycle, recovery, orchestration, evidence/handoff, and capability gating.

## Strengths to preserve

The current Skill is unusually strong in areas that most public Skills do not cover systematically:

- ChatGPT Window != Workflow Session;
- exact Session/Goal/Task/Job recovery;
- never redispatch pending work after Host interruption;
- capability gating for CodingAgent/LSP/Plugin/continuation;
- Job vs detached process vs persistent shell;
- delegated-result pullback to controller/user;
- failure evidence immutability;
- separation of project lifetime from model-turn lifetime.

These are the differentiating core.

## Software-engineering coupling to isolate

The current Skill still treats software as the default model in several places:

- frontmatter says "software-engineering projects" / "code project";
- Git/worktree is presented as a core state layer;
- validation is code-centric;
- failure examples include parser/schema/database semantics;
- closeout assumes refs/worktrees/branches;
- routine autonomy examples are implementation/tests/commits.

These should become a software-engineering domain adapter/reference instead of the universal WebCodex model.

## Proposed generic control loop

```text
1. Resolve intent and exact WebCodex execution context.
2. Discover current capabilities and authority.
3. Select the smallest durable scope needed.
4. Observe state and reconcile uncertain prior work.
5. Acquire/isolate resources needed for the bounded action.
6. Execute one bounded action/batch.
7. Re-observe and verify the state transition.
8. Persist evidence/checkpoint/next action when recovery matters.
9. Continue autonomously until a true decision boundary.
10. Release resources and close out deliberately.
```

## KEEP / ADOPT / REJECT

### KEEP

- exact identity discipline;
- short bounded model turns;
- Job recovery;
- Session/Goal/Task separation;
- capability gating;
- delegated result pullback;
- failure evidence preservation;
- explicit user-decision boundaries.

### ADOPT

- generic observe -> act -> verify;
- stale-handle/generation invariant;
- acquire/borrow -> release resource lifecycle;
- durable run-state/evidence manifest beyond Git;
- one-owner-per-contract reference organization;
- live runtime manifests for volatile contracts;
- old-skill/no-skill eval baselines with time/token metrics;
- trigger-overreach evals;
- formal Skill composition protocol.

### REJECT / DO NOT ABSORB INTO CORE

- generic TDD/software-architecture/security/database expertise;
- Git as universal project state;
- worktree as universal isolation;
- software validation ladders as global rules;
- domain-specific research methodology;
- browser command manuals already owned by browser/runtime Skills;
- static copies of rapidly changing WebCodex schemas.
