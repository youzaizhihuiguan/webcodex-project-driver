# WebCodex Project Driver Benchmark — Round 2

Date: 2026-10-06

## Purpose

Round 2 converts Round 1 observations into a concrete WebCodex control-plane design.

The focus is no longer "what good software-development Skills do." The focus is:

> What invariants should a Skill enforce when controlling WebCodex across projects, Sessions, Jobs, browser/computer surfaces, remote execution, artifacts, optional delegated agents, and interrupted model turns?

This round uses two evidence classes:

1. current WebCodex live tool manifests;
2. current external Agent Skill / orchestration guidance.

No production Skill files are changed in this round.

---

## Finding 1 — Separate durable identity from freshness proof

WebCodex exposes both durable identities and bounded freshness selectors.

### Durable identities

Examples:
- Project id;
- Workflow Session id;
- message id;
- AgentTask id;
- Agent identity;
- Job id;
- browser id;
- page id.

These identify the durable or process-local object being addressed.

### Freshness / replay selectors

Examples observed in live manifests:
- `assignment_fence` from `get_session_assignment`;
- `attempt_fence` + `attempt_controller_generation`;
- `attempt_ref` as an exact compact selector;
- Job `observation_token` / `observation_ref`;
- Browser `element_id` admitted by the current snapshot;
- browser diagnostics `since_cursor`;
- completion / idempotency keys;
- wake consume tokens where active-turn lineage matters.

These do not identify "the task" in the general sense. They prove that the caller is acting against the exact current snapshot/attempt/generation expected by the operation.

### Proposed rule

For every stateful WebCodex operation, distinguish:

```text
object identity
+
freshness / generation proof
+
authority
```

Never treat one as a substitute for another.

## Finding 2 — Use a universal Observe → Act → Verify loop

The browser runtime explicitly requires snapshot-admitted actions and re-observation after structural changes.

AgentTask operations require an exact Attempt and reject stale generation/fence state.

Session completion requires the exact assignment fence.

Job observation uses a Job-bound observation token/reference.

This supports one generic control loop:

```text
OBSERVE
  Resolve current state, exact object identity, freshness selector and authority.

RECONCILE
  If earlier execution may already exist, inspect it before creating replacement work.

ACT
  Perform one bounded effect using the current selector/fence.

VERIFY
  Re-observe enough state to establish what actually changed.

PERSIST
  Save durable evidence / next action when recovery matters.
```

This should replace software-specific "read -> edit -> test -> commit" as the universal core.

## Finding 3 — Reconcile-before-retry must be non-negotiable

Live WebCodex manifests repeatedly encode replay or stale-state safety:
- Session completion has `completion_key` plus assignment fence;
- AgentTask Attempt start is keyed and returns the same Attempt on exact retry;
- endpoint continuation is fenced replay;
- Job observation never launches/retries the Job;
- browser effect uncertainty instructs the caller to observe instead of retrying blindly.

### Proposed invariant

> If outcome is uncertain, never dispatch replacement work until the exact prior identity has been reconciled.

This is broader than interruption recovery. It applies to:
- lost chat responses;
- transport timeouts;
- browser action uncertainty;
- background Job handoff;
- AgentTask delegation;
- Session assignment completion.

## Finding 4 — Trigger on WebCodex control need, not domain

Official Skill description guidance warns that over-broad descriptions cause false activation. It recommends realistic positive and near-miss negative trigger evals, multiple runs, and train/validation separation.

The Project Driver should not trigger merely because the prompt mentions:
- code;
- research;
- browser;
- data;
- server;
- files.

It should trigger when the user needs WebCodex to **execute or continue substantial stateful work**.

### Should usually trigger

- continue a multi-step WebCodex project;
- inspect and modify a project with durable checkpoints;
- recover after interruption or context loss;
- launch/recover a long Job;
- operate Browser/Computer through WebCodex across several actions;
- coordinate Sessions/Goals/AgentTasks;
- run work on a remote/persistent environment via WebCodex;
- move artifacts across registered projects;
- manage phase/state/evidence across multiple model turns.

### Should usually not trigger

- explain code without touching a WebCodex project;
- answer a conceptual software question;
- summarize a pasted document;
- one-off web search that does not use WebCodex;
- simple arithmetic/data reasoning;
- tiny writing request;
- generic research answer completed entirely in chat.

See `trigger-evals-draft.json`.

## Finding 5 — Define the smallest cross-domain run manifest

Git commit/branch/worktree is powerful but software-specific.

Research systems instead persist state, run artifacts, evidence and handoff metadata.

Browser systems persist session/snapshot/ref state.

Remote/long-running workflows persist Job/shell/host identity.

### Proposed minimum manifest

Every substantial WebCodex workflow should be able to persist:

```text
run_id / durable scope identity
objective
current phase/state
exact execution context
known active work identities
evidence / result locations
resource ownership
last verified state
next allowed action
decision blockers
```

Optional domain extensions may add:
- Git SHA/ref/worktree;
- research source/evidence paths;
- browser/page/snapshot identifiers;
- SSH resource/shell identity;
- database namespace;
- experiment config/hash.

See `run-manifest-v0.2.md`.

## Finding 6 — Treat resource lifecycle as a first-class contract

A WebCodex controller can acquire or create:
- worktrees;
- Projects;
- Jobs;
- persistent shells;
- SSH bindings;
- browser/pages;
- computer surfaces;
- transferred artifacts;
- AgentTask Attempts;
- continuation registrations.

The control layer should track which resources are:
- borrowed;
- owned;
- persistent;
- ephemeral;
- safe to leave running;
- required to release/close.

### Proposed lifecycle

```text
ACQUIRE / ATTACH
-> USE
-> VERIFY
-> HANDOFF or RELEASE
-> FAILURE CLEANUP
```

Do not apply destructive cleanup automatically when preservation is important to recovery/evidence.

## Finding 7 — Skill composition requires ownership boundaries

External Skill guidance supports composition, but composition without ownership creates contradictions.

### Proposed ownership model

**webcodex-project-driver owns:**
- WebCodex runtime/capability discovery;
- execution context selection;
- durable identity/freshness discipline;
- WebCodex long-job lifecycle;
- WebCodex resource lifecycle;
- interruption recovery;
- Session/Goal/Task orchestration;
- result/evidence handoff;
- control-plane decision boundaries.

**Domain Skills own:**
- research methodology;
- security criteria;
- software architecture quality;
- database design;
- document formatting;
- statistical methodology;
- domain-specific validation.

**Project-local instructions own:**
- frozen architecture;
- business rules;
- thresholds;
- acceptance criteria;
- risk policy;
- branch/merge policy;
- sensitive project-specific constraints.

### Precedence

Subject to platform/system authority:

```text
project-local explicit contract
> domain Skill's domain-quality rule
> Project Driver generic heuristic
```

Project Driver still owns WebCodex safety/recovery semantics even when a domain Skill is active.

See `composition-v0.2.md`.

## Finding 8 — Do not statically copy volatile WebCodex schemas

agent-browser provides a useful pattern: install a thin stable discovery Skill, then load version-matched instructions from the installed runtime.

WebCodex already provides:
- live tool manifests;
- runtime status;
- capability discovery.

### Proposed rule

Static references should explain:
- concepts;
- invariants;
- selection logic;
- recovery principles.

Static references should not duplicate:
- rapidly changing tool schemas;
- current provider/model catalogs;
- runtime-specific availability;
- exact optional arguments that can be discovered live.

## Finding 9 — Skill evaluation must cover routing and behavior separately

Two different failures matter:

### Trigger failure

The Skill:
- fails to activate when needed;
- activates on trivial or unrelated tasks.

### Behavior failure

The Skill activates, but then:
- resumes the wrong Session;
- duplicates a Job;
- uses a stale fence/ref;
- forces Git on a research workflow;
- fabricates unavailable delegation;
- fails to surface delegated result content;
- forgets cleanup/handoff.

Official Agent Skills guidance recommends:
- with-Skill vs baseline/old-Skill runs;
- clean contexts;
- assertion-based grading;
- timing/token capture;
- blind comparison when useful;
- mechanical scripts for mechanically checkable assertions.

### Proposed first eval suite

1. ambiguous "continue" with multiple Sessions;
2. pending Job after chat interruption;
3. Session todo resolved but answer body not shown;
4. stale Browser element after document change;
5. AgentTask API present but no CodingAgent provider;
6. research workflow where Git should not become mandatory;
7. software workflow where exact SHA/worktree matters;
8. remote long process requiring Job/shell ownership distinction;
9. resource borrowed then task fails: cleanup/handoff behavior;
10. trivial conceptual question that should not trigger Project Driver.

## Proposed v0.2 core model

```text
1. Decide whether this is a substantial WebCodex control task.
2. Resolve exact execution context and project/run identity.
3. Discover current capabilities, authority and optional backends.
4. Observe current state; reconcile uncertain prior work.
5. Select the smallest durable scope and needed resources.
6. Acquire/attach resources.
7. Execute one bounded action/batch with current freshness proof.
8. Re-observe and verify the intended state transition.
9. Persist evidence, current state and exact next action if recovery matters.
10. Continue automatically while policy allows.
11. At a real decision boundary, ask the user.
12. Handoff/release/close resources deliberately.
```

This model applies equally to:
- code changes;
- research phases;
- browser workflows;
- remote Jobs;
- data experiments;
- artifact operations;
- multi-Agent coordination.

## v0.2 implementation recommendation

Do **not** rewrite the production Skill yet.

Next steps:

1. run trigger evals on the current description;
2. run behavior evals against current Skill;
3. identify which failures are real rather than theoretical;
4. then refactor the Skill around the generic control loop;
5. move Git/software-specific rules into a software domain reference;
6. rerun the exact same eval suite against v0.2;
7. promote only if v0.2 improves correctness without unacceptable token/time overhead.
