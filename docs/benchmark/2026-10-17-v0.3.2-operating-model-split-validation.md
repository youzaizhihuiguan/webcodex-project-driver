## Managed-worktree policy

The candidate implements the Phase A evidence-backed policy:

1. **Default to an existing suitable checkout.**
2. Create a managed worktree only for a concrete filesystem-isolation or preservation need, including:
   - concurrent mutable branches/tasks that would conflict;
   - preserving a stable checkout while another candidate is developed;
   - preserving a failed/experimental workspace that must remain inspectable;
   - an actually required independent audit whose filesystem isolation is material.
3. `substantial`, `review`, and `long-running` are explicitly insufficient reasons by themselves.
4. Reuse a compatible managed worktree only after repository/ref/state/active-owner/evidence checks.
5. Treat generated-output footprint separately from Git worktree metadata.
6. Use the Phase A measured failure mode — replicated Rust `target/` output dominated the >100 GiB footprint — to motivate output-aware capacity review.
7. Use Git/WebCodex-aware terminal cleanup only after active ownership, unique uncommitted state, durable refs, retained evidence, and authority are reconciled.
8. Treat registry/filesystem drift as a reconciliation finding, not as automatic deletion authority.
9. Keep branch/ref deletion separate from worktree removal.
10. Verify expected state/disk change after cleanup.

No worktree or generated-output cleanup was performed in Phase E.
