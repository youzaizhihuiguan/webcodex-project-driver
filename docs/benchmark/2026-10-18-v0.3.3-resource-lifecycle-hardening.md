# v0.3.3 — Resource Lifecycle Hardening Validation

Date: 2026-10-18

Status: **IMPLEMENTED / PACKAGE VALIDATION PENDING**

Scope: targeted hardening after real LlamaLab resource-leak incidents. This change keeps `webcodex-project-driver` as the WebCodex-specific owner of resource/scratch/worktree lifecycle and does not add a new Skill or move WebCodex mechanics into `agent-operating-model`.

## Real failure evidence that motivated the change

The live LlamaLab audit found all of the following after M3/G3 work:

- the authoritative Mac M3 worktree retained about 34.0 GB of `src-tauri/target` plus `node_modules`, `dist`, `.m3-scratch`, and M3.5/G3 transport archives after G3 had already passed;
- one historical Mac review worktree alone retained about 4.2 GB of Cargo target output;
- twelve additional clean detached review worktrees remained even though their commits were already contained by the authoritative M3 branch;
- Windows native-validation workspaces were created under `D:\ai\llama\启动器` instead of configured WebCodex scratch;
- eight audited M3.3/M3.4 Windows validation directories consumed about 59.38 GB, including one directory around 36.46 GB and another around 11.46 GB;
- source/frontend transport archives and repeated extracted source/build trees were retained after their validation purpose ended;
- historical control-plane objects remained active long after their owning phases were terminal: 39 historical Sessions were closed during cleanup and temporary/stale Project registry entries required explicit reconciliation.

The cleanup verified that these were lifecycle leaks rather than required authoritative state: G3 was `PASSED / M3 COMPLETE / M4.1 NOT_STARTED`, the extra review worktrees were clean and contained by the durable branch, and required formal evidence was already persisted.

## Design references

The hardening adopts established patterns rather than inventing a new cleanup framework:

- **GSD** — creation-time worktree manifest and manifest-scoped cleanup; missing provenance blocks broad worktree discovery cleanup.
- **Superpowers** — no implicit worktree creation; already-isolated environments are reused and worktree creation requires explicit consent/authority.
- **Worktrunk** — lifecycle hooks tie setup and teardown to the worktree resource rather than relying on later memory.
- **OpenAI Agents sandbox runtime** — caller-owned and runner-owned resources have distinct cleanup authority; runner-owned cleanup is idempotent.
- **agentctl** — cleanup is state-derived and retryable; task state is retained when cleanup partially fails.
- **Kubernetes owner/finalizer model** — terminal work and resource deletion are distinct; unresolved finalizers keep cleanup pending.
- **Docker/systemd temporary-resource practice** — conservative deletion of unknown state and scoped age/ownership-based fallback cleanup.
- **Cargo** — build output can be relocated with standard target-dir mechanisms and shared compilation caching should use supported mechanisms such as `sccache`, not ad-hoc cross-worktree target sharing.

## Implemented contract

### 1. Placement admission

Before WebCodex creates a disk-material resource, it resolves:

- exact owner;
- approved destination;
- retention class;
- cleanup condition/finalizers;
- applicable user/project authority.

Configured scratch remains:

- macOS: `/Users/youzai/ai/scratch`
- Windows: `D:\ai\scratch`

WebCodex-created non-Git validation source copies, transfer staging, raw evidence, and task-scoped generated state default there.

### 2. Ownership/provenance

Temporary resources use creation-time provenance rather than later path guessing.

The resource/task manifest records enough to recover exact owner, Runner, path, source candidate, retention class, lifecycle state, cleanup triggers/finalizers, and promoted durable results.

### 3. Worktree admission

An existing suitable checkout remains the default.

`fresh reviewer`, `independent review`, `review`, `substantial`, and `long-running` do not by themselves justify filesystem isolation.

New managed worktree allocation requires concrete isolation value plus existing user/project authority or an explicit allocation decision.

### 4. Generated-output independence

Source/worktree retention no longer implies retention of:

- Cargo target/build output;
- dependency trees;
- dist/build/out directories;
- transport archives;
- extracted validation copies.

Task-specific toolchain output should use task scratch when supported by project/toolchain policy.

### 5. Evidence promotion

Raw logs/screenshots/JSON/transport/source/build material starts staged in scratch.

Only the minimum evidence required by the owning validation/project contract is promoted durably.

Failed formal evidence is preserved as required provenance/result without automatically retaining the complete reproducible build workspace.

### 6. Finalization and cleanup_pending

Substantive terminal state and resource lifecycle closure are separate.

Owned resources pass through:

~~~text
ADMIT
-> ALLOCATE / ATTACH + REGISTER OWNERSHIP
-> USE
-> PROMOTE durable results
-> FINALIZE
-> RECLAIM
-> VERIFY CLOSED
~~~

If cleanup partially fails, exact state remains `cleanup_pending`; later recovery continues only the unresolved cleanup delta.

### 7. Pre-allocation reconciliation

Before another heavy worktree/validation workspace/build is allocated for the same Project, known terminal or `cleanup_pending` owned leftovers are reconciled first.

This is manifest-scoped recovery, not broad filesystem garbage collection.

## Behavior regressions

New focused evals:

- **B30** — Windows/non-Git native validation uses configured scratch rather than a convenient project/user directory.
- **B31** — fresh read-only reviewer does not imply a fresh worktree.
- **B32** — new worktree allocation requires concrete isolation need, recoverable provenance, and applicable consent/authority.
- **B33** — keep authoritative worktree while reclaiming unneeded 30+ GiB build output.
- **B34** — source/destination transport archives, extraction trees, and build outputs are finalized after durable receipt promotion.
- **B35** — preserve failed evidence without treating a multi-GiB build tree as durable evidence by default.
- **B36** — partial cleanup leaves `cleanup_pending` and retries only the unresolved delta.
- **B37** — ownership-unknown large directories are protected/report-only until explicitly authorized.
- **B38** — prior terminal owned leaks are reconciled before another heavy allocation.

## Non-goals

This hardening does not:

- add a new cleanup/resource-manager Skill;
- move WebCodex resource semantics into `agent-operating-model`;
- invent a global GC daemon or second task database;
- automatically delete unknown/foreign/dirty resources;
- force all projects to share one Cargo target directory or install `sccache`;
- make worktree creation mandatory for review.
